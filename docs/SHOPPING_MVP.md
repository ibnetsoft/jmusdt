# 쇼핑몰 1차 구현 (2026-10-28)

**후속 변경:** 신규 상품 가격과 결제는 포인트 단위로 전환했다. 1 USDT = 1 P 양방향 스왑은 `/points`에서 처리한다. 아래 USDT 직접 결제 설명은 최초 구현 이력이며 현재 동작은 [포인트 안내](POINTS.md)를 따른다. 기존 주문의 USDT 결제 단위는 보존한다.

## 사용 방법

- 관리자: `/admin`의 **상품 관리** 또는 `/admin/shop`.
- 상품명, 대표 이미지 HTTPS URL(선택), 상세 설명, USDT 가격(소수점 6자리), 재고를 입력한다. 판매 중을 체크하고 저장하면 사용자에게 공개된다.
- 상세 설명은 줄바꿈을 유지하는 텍스트다. HTML/script를 실행하지 않는다. 이미지 파일 업로드·리치 텍스트 CMS는 이번 구현에 포함하지 않는다.
- 사용자: 지갑의 **쇼핑몰** 메뉴 또는 `/shop` → 상품 상세 `/shop/[id]` → 수량 → **USDT 결제 확정**.
- 결제 후 주문번호와 구매 내역을 확인한다. 지갑 거래내역에도 쇼핑몰 상품 구매가 표시된다.
- 관리자 수정은 버전 충돌을 검사한다. 판매 중 해제로 비공개 처리하며 기존 주문의 상품·가격 스냅샷은 보존된다.

## 금액과 데이터

`db/commerce.sql`을 기존 `db/schema.sql` 이후 적용한다. `npm run db:apply`는 두 파일을 같은 트랜잭션으로 적용한다.

주문·잔액 차감·재고 차감·불변 균형 원장을 단일 DB 함수에서 처리한다. 서버 가격과 버전을 사용하며 클라이언트 가격을 신뢰하지 않는다. 동일 회원/요청키 재시도는 기존 주문을 반환하고, 다른 상품·수량·버전으로 재사용하면 거부한다. 판매가·재고 변경 후에는 최신 상세 내용을 다시 확인해야 한다. 상품 저장과 구매 모두 버전을 증가시켜 관리자가 오래된 재고를 덮어쓰지 않도록 한다.

USDT는 bigint micro-units, 판매대금 상대 계정은 `shop:revenue`다. 내부 원장 결제이며 주문별 온체인 송금은 없다. 지갑 네트워크가 Nile인 현재 배포는 실제 USDT 운영 결제가 아닌 테스트 환경이다.

인증 회원만 상품·주문을 조회하고 본인 주문만 읽는다. 상품 생성/수정은 서버 관리 관리자 권한을 확인한다. 브라우저 DB 역할은 구매 함수를 직접 실행하거나 잔액·상품을 변경할 수 없다. 관리자 작업은 감사 기록을 남긴다.

## 검증

- `npm test`: 기존 원장·서명 테스트와 신규 쇼핑 결제 테스트. 중복 요청, 한도 내 정확한 차감, 원장 합계 0, 재고/가격/잔액 충돌, 주문 스냅샷, 브라우저 역할의 함수 실행 거부를 확인한다.
- `npx tsx scripts/verify-commerce.ts --test-account`: 실제 Supabase에 임시 일반/관리자 계정을 만들어 HTTP 상품 등록·발행·비공개·수정 충돌·권한·잔액 부족 거부를 확인한다. 실제 PostgreSQL 결제는 롤백 전용 트랜잭션에서 검증해 테스트 금액·주문을 남기지 않는다. QA 상품·프로필·세션·계정을 정리한다. `APP_ORIGIN`을 검증할 배포에 맞춰 실행한다.
- 타입 검사·프로덕션 빌드를 확인한다. Next.js 16.4.3, @next/env 16.4.3, Zod 4.6.7로 보안 업데이트했다.

## 이번 범위 밖

마케팅 보상·주머니·데일리수당은 연결하지 않았다. 배송지·배송 추적·환불/취소·상품 옵션·이미지 업로드는 후속 단계다. 주문은 결제 완료를 기록하며 배송 완료를 뜻하지 않는다. 운영 판매에 필요한 배송/환불 업무는 별도 구현해야 한다.
